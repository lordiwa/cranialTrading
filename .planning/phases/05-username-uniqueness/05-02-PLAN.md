<objective>
Establish the atomic uniqueness primitive (UNIQ-02): a `/usernames/{normalizedUsername}` index collection with create-only Firestore rules (D-01, D-02), plus the `reserveUsername` / `releaseUsername` helpers in `src/stores/auth.ts` (D-09) that every creation path will use. The create-only rule (no `update`) is what makes uniqueness atomic with zero TOCTOU and no transaction (D-02).

Purpose: This is the foundation that fixes the SCRUM-70 root cause — duplicate `@rafael_m` docs existed because there was no atomic guard. A `setDoc` onto an existing reservation is evaluated by Firestore as an `update` (resource != null) and is denied; that `permission-denied` IS the "taken" signal (D-02, D-03). reserveUsername catches it and returns false; releaseUsername is best-effort cleanup for changeUsername.

Output: a new `/usernames/{username}` block in `firestore.rules` (a top-level sibling inserted after the `/users/{userId}` block closes, before the catch-all deny); two helpers in auth.ts; a small unit test mocking firebase/firestore.
</objective>

```typescript
    /**
     * Reserve a username atomically via the /usernames index (D-09).
     * The create-only Firestore rule denies a write onto an existing doc, so a
     * permission-denied here means "already taken" → return false. Any other
     * failure is also treated as not-reserved (safe default).
     * @param norm MUST be a normalized username (use normalizeUsername upstream).
     */
    const reserveUsername = async (uid: string, norm: string): Promise<boolean> => {
        try {
            await setDoc(doc(db, 'usernames', norm), { uid, createdAt: new Date() });
            return true;
        } catch {
            return false;
        }
    };

    /**
     * Release a username reservation (best-effort, D-09). Used by changeUsername
     * to free the previous username. Never throws.
     */
    const releaseUsername = async (norm: string): Promise<void> => {
        try {
            await deleteDoc(doc(db, 'usernames', norm));
        } catch {
            // best-effort: a dangling reservation is acceptable, swallow.
        }
    };
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous client → /usernames read | Unauthenticated registration availability check reads the index (D-02 read=true) |
| Authed client → /usernames create | An authed user reserves a username; Firestore rules enforce uid ownership |
| Authed client → /usernames delete | Owner releases their own reservation (changeUsername path) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Spoofing | create rule with forged uid | mitigate | `create: request.resource.data.uid == request.auth.uid` — a user cannot reserve a username pointing at another uid |
| T-05-02-02 | Tampering | hijack existing reservation via setDoc/update | mitigate | No `update`/`write` rule; setDoc onto existing doc is an UPDATE and is denied — the core uniqueness guarantee (D-02) |
| T-05-02-03 | Information Disclosure | anonymous read of /usernames exposes which usernames exist + their uid | accept | Consistent with existing public `/users` read (D-02); username→uid mapping is already inferable from public profiles; no PII beyond what `/users` already exposes |
| T-05-02-04 | Elevation of Privilege | non-owner deletes a reservation to free/steal a name | mitigate | `delete: resource.data.uid == request.auth.uid` — only the owner can release |
| T-05-02-05 | Denial of Service | adversary mass-reserves usernames | accept | Requires auth per reservation; abuse is bounded by account creation; out of scope (no reserved-name blocklist this phase, deferred) |
</threat_model>
